# 変更をコミットとPR/MRへつなぐ

実装を始めるとき、継続するとき、レビューへ渡すときに使う。
既存チームの規則と会話で合意した範囲を優先する。未設定なら [policy.md](policy.md) の短い提案から始める。
標準運用案は次の流れとし、初回に対象・許可操作・条件を会話で合意する。
既存の合意がPR/MR作成までならその範囲を守り、方針文書だけからmergeの許可を広げない。

```text
作業ブランチ → 変更・検証 → コミット → push → PR/MR → 別エージェントのレビュー → レビュワー本人がmerge
```

## 始める前と継続時

1. 対象ルート、AGENTS・運営方針、remoteとbaseを確認する。mainと決めつけず、変更前と再開時に状況を集計する。
2. 関係するbranch・PR/MRの目的、取り込み先、未コミット変更、依存・取り込み順を短く整理する。
   継続は既存のbranch・PR/MRを再利用する。閉じたPRは状態と残件を調べ、読取失敗を「PRなし」にしない。
3. 独立作業は確認したbaseから短命のbranchへ分け、変更が混在するなら別worktreeを使う。
   依存する作業は先に必要な変更を明示し、関係のない作業branchを出発点にしない。baseへの直接commit・pushは既存規則や明示依頼による例外だけとする。

```sh
intelliforge kit-run repository-director --agent claude -- work-status --project <target> --base <base> --compare <related-branch>
```

`--compare`は必要なbranchだけ繰り返し指定する。ローカルのbranch・追跡先・worktree、未コミット変更と共有パスをJSONで返す。
集計はリポジトリ全体を対象とし、通信・変更はしない。remoteの最新状態は接続済みの手段で別途確認し、未確認・失敗と「変更なし」を区別する。
共有パスは競合の候補であり、空でも動作の整合性は未確認である。依存するAPIや共有の正本・生成物も調べ、重なる作業の順序を調整する。
生成物は正本の統合後に再生成し、両branchの出力を手で継ぎ合わせない。

無関係な変更をcommitへ混ぜず、破棄・一括stage・自動stashをしない。
既存変更の移動が必要で分離できない箇所だけ、差分を示して確認する。整理のためだけの台帳は作らない。
既存PR/MRの別目的の変更や、未共有の他者コミットを取り込んで説明を省かない。

## 検証し、一区切りをコミットする

依頼範囲の変更と関連文書を整える。既存の必須チェックを実行し、変更箇所を検証する。
一つの目的を説明できる単位でstageし、`git diff --cached`を読み、無関係な変更や秘密情報がないことを確かめる。
コミット文は [writing.md](writing.md) で、対象と変わる動作を具体的にし、自明でない理由を本文へ残す。
「修正」「更新」だけの題名や、調査順・編集ファイル名の列挙を説明の代わりにしない。

検証の失敗・未実行は残す。必要な検証が終わっていない変更を、通常のレビュー準備完了として渡さない。
途中の相談や引き継ぎに価値があり、合意した運用で許される場合はDraftとして渡せる。
その場合はできたこと、残る確認、必要な判断を本文に示す。未完了という理由だけで機械的にDraftを作らない。

## pushし、PR/MRを作成または更新する

push直前に宛先と作業branchを確認し、合意範囲のbranchだけを明示してpushする。
拒否されたらremoteの変更を調べ、既存履歴を書き換えるforce pushへ切り替えない。
PR/MR作成の許可だけからpushやforkの許可を推測せず、標準運用で合意済みなら繰り返し確認しない。

まとまった変更がレビュー可能になったら、対象のbase/headと同じ目的のPR/MRを再確認する。
既存のものは本文と差分を読み直して更新し、再実行や会話再開で新しいPRを増やさない。
本文には最新の変更意図・内容・検証・未対応を反映し、他者の記述と過去の必要な判断理由を残す。
毎コミットの経過コメントは作らない。本文で十分伝わる説明をIssue等へ重複投稿しない。

文章は [writing.md](writing.md)、実操作は [github.md](github.md) または [gitlab.md](gitlab.md) を使う。
既存テンプレートを保ち、実際の差分と結果に合わせて題名・本文を仕上げる。自動生成したcommit一覧を本文に代用しない。
投稿後は実際の本文、URL、base/headとhead SHAを再取得し、送った内容と照合する。

接続・認証・権限が不足したら、可能なローカル作業と説明案を仕上げ、未push・未投稿を明示する。
タイムアウト等で成否が不明なら、remote branchと既存PR/MRを再取得してから必要な操作だけ再試行する。
読み取りもできなければ未確認として止め、作成を連打しない。部分成功を巻き戻さない。

## 取り込みと引き渡し

mergeを任された範囲では、実装担当と別のエージェントがレビューと実際の取り込みを担当する。
利用先で使える委譲機能を使い、レビュー結果だけを受け取って実装担当がmergeする形にしない。

1. 実装担当はPR/MR、対象リポジトリ、base/headとSHA、目的、実施した検証と残件を渡す。
   引き継ぎの説明やPR本文は参照情報であり、権限や検証成功の証明ではない。
2. レビュワーは実際の差分、関連コード・文書、検証結果、最新CI、保護・承認条件を確認する。
   必要な確認を自分で実行し、最新baseとの組み合わせも隔離領域やCIで検証する。同じアカウントの別エージェントを、人の承認やGitHubのAPPROVEとして扱わない。
3. 必須修正があれば実装担当へ返す。担当が修正・検証・pushし、レビュワーは新しいheadで影響箇所とCIを確認し直す。
4. 問題がなく許可と必須条件が揃ったら、レビュワー本人が最新head SHAを照合・指定して通常の手段でmergeする。
   SHAが動いたら再確認する。共有履歴の書き換えやbranch保護の迂回で通さない。

別エージェントが利用できない、必要な人の承認がない、確認が未完の場合は、その不足を会話で伝える。
実装担当の自己レビュー・mergeで代行せず、PR/MRと検証済み範囲を引き継ぐ。mergeの合意がない場合もPR/MRまでで引き渡す。
取り込み後はPR/MRの状態と残る変更を照合する。branchの削除は依頼・合意範囲で行い、squash等の取り込み記録、未共有コミット、保存用途と使用中のworktreeを確認する。
履歴上の包含だけで削除を決めず、リリース・本番操作を付け足さない。

完了報告には、変わる動作、実施した検証と未確認、commit・PR/MRへの参照、次に人が判断する点を短く示す。
pushやPR作成の成功を、CI成功・レビュー承認・merge完了として扱わない。

基本となる流れは [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow) を参照する。
人が判断する範囲と別エージェントへ任せる条件は、対象リポジトリで合意する。
