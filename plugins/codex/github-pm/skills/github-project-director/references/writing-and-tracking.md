# Issue・PR・コメントを、あとから読んでも分かる文章にする

投稿・提案文を作成または編集するときに読む。読者は開発者と非開発者の両方で、
会話や実装の経緯を知らない人を基準にする。リポジトリのテンプレートや言語指定を優先し、
指定がなければ依頼の言語を使う。以下の構成は基本形であり、すべての見出しを毎回付けない。

## 投稿判断：重要な変化だけを残す

スキルの起動、調査、Project更新は、それだけではコメントを作る理由にならない。
まず会話・対象Issue本文・関連PR・関連コメントを読み、次の順に判定する。

1. **共有価値**：人の判断が必要な障害、合意した方針・範囲・完了条件の変更、完了・引き渡しの要点か。
   調査開始、作業中、再試行、個々のテスト成功、フィールド更新の言い直しは投稿しない。
2. **新情報**：同じ成果や判断が既に本文・関連PR・コメントで十分分かるなら追加投稿しない。
   日付・言い回し・entry-keyが異なるだけでは新情報にならない。確認不能なら重複なしと断定しない。
3. **範囲と場所**：依頼または合意済み運用で投稿が許可されているか。その判断や成果を扱う場所を一つ選ぶ。
   個別の判断は該当Issue、実装と検証はPR、状態・担当は既存フィールド、横断的な定例は合意済み記録先へ。

通常は一区切りにつき一つの報告にまとめる。新たな判断が必要な障害は区切りを待たずに扱う。
重要な障害は、未承認だからと黙らず会話で知らせる。GitHub投稿が未承認なら必要な下書きまで用意する。
明示的な記録依頼はその範囲で扱うが、明示された例外がなければ同じ内容を再投稿しない。
明示依頼も合意済み運用もない定例を付け足さず、記録先がないだけで新Issueを提案しない。
変化がなければ投稿しない。「記録しなかった」という記録や、不要な投稿の承認確認も作らない。
本文編集が依頼範囲なら現行要件を更新する。判断理由も本文で伝われば説明コメントを重ねない。
過去の判断・他者の記述を無断で消さない。同じ内容を親Issue・個別Issue・定例へ転載しない。

途中経過は必要に応じて会話内で伝える。再開時は既存Issue・PR・git履歴・既存の引き継ぎ資料を参照し、
このSkillのためだけに作業日誌、別DB、Memory保存を増やさない。

## 共通の書き方

最初の1〜2文で、誰が何に困り、今回どう変わるかを伝える。保守作業なら、運用や開発上の
具体的な問題を示す。無理に利用者の物語に変換しない。作業順ではなく読者が理解しやすい順に書く。

- タイトルは対象と変化が分かる文にする。「基盤の高度化」「整合性の担保」だけで終わらせない。
- 専門用語・略語・内部コード名は判断に必要なものだけ残し、初出で日常語による短い説明を添える。
  一文に複数の専門用語を詰めない。日常語で意味が伝わるなら、hydrate等の原語を括弧で足さない。
  ファイル名や識別子は必要な実装詳細にまとめる。
- 具体的な操作と、その前後で変わる振る舞いを示す。短くするために完了条件や重要な制約を落とさない。
- 箇条書きは並列の事項や手順に、表は比較に使う。長い表、深い入れ子、同じ説明の繰り返しを避ける。
- 事実、提案、未確認を区別する。テストの成功を利用者の承認や本番動作の証明にしない。
  依頼にない実装方式・代替環境・復旧後の予定を確定事項にしない。必要なら実装案／提案と明示し、
  短い報告に不要なら省く。文例の選択肢や予定を、実案件で決まったこととして転記しない。
- 投稿前に、冒頭だけで目的が分かるか、残作業が成果に紛れていないか、用語やリンクを追わずに
  主旨が分かるかを読み直す。同じ意味の語句・文を重ねない（「後から続きから再開」→「後から再開」、
  「API停止で結合確認できない。結合確認は未完了」→「API停止で結合確認を進められない」）。
  執筆手順やこのチェック自体を投稿本文に入れない。

## Issue

**目的 / やること / 完了条件 / 関連** は内容の目安。短いIssueでは冒頭の説明と完了条件だけでもよい。
再現が必要な不具合は発生条件・現在の動作・期待する動作も示す。
本文は作業日誌にせず、現行の目的・範囲・完了条件を読める状態にする。
長い仕様・操作ログ・ファイル一覧は既存の関連資料へ寄せる。ただし本文だけで目的・完了条件・重要な制約が分かること。
リンク先だけに必須条件を隠さない。専門用語の説明や全見出しを増やして文章を膨らませない。
完了条件は確認できる動作にする。実装案が未決定なら、要件と混ぜず「実装案」と明示する。

改善前：
> セッション永続化の整合性を担保するため、認証ライフサイクルの再設計と状態遷移の最適化を実施する。

改善後（仮の不具合例）：
> **画面を再読み込みしてもログインを維持する**
>
> ログイン後に画面を再読み込みすると、再びログインを求められます。有効期限内は、そのまま作業を続けられるようにします。
>
> **やること**
> - 再読み込み後にログイン状態を復元する。
> - 有効期限が切れている場合は、ログイン画面へ案内する。
>
> **完了条件**
> - 有効期限内の再読み込みで、開いていた画面を引き続き使える。
> - 期限切れの状態では、ログインを求められる。

## PR

基本は **目的 / 変更内容 / 確認結果 / 関連Issue**。小さな変更なら短い本文と確認結果だけでよい。
冒頭に変更前後の動作を書き、必要な実装詳細はその後に置く。レビューで判断が必要な点や未対応部分は隠さない。
実施した確認と未実施の確認を区別し、出力ログを丸ごと貼る代わりに確認内容と結果を書く。

改善前：
> auth hookをリファクタしてhydrateのraceを解消。CI green。

改善後（確認結果を含む架空の記載例。実際のPRでは観測した事実に置き換える）：
> 画面の再読み込み時に、一瞬ログイン画面へ戻る問題を修正しました。
> 保存されたログイン情報の読み込みが終わるまで、画面の切り替えを待つようにしています。
>
> **確認結果**
> - 有効期限内の再読み込みでログイン画面へ戻らないことを自動テストで確認しました。
> - 期限切れの場合にログイン画面へ移るテストも成功しています。
> - 実ブラウザーでの確認は未実施です。
>
> 対応する不具合：#123「再読み込み時にログイン画面へ戻る」

## レビューコメント

位置・発生条件・問題・影響を具体的に書き、修正案があれば続ける。根拠のない断定はしない。
**修正が必要な指摘**と**任意の改善案**を区別し、個人の好みを不具合として扱わない。

改善前：
> null handlingが甘い。guardを追加すべき。

改善後（架空のコード例）：
> **修正が必要：未ログイン時に画面が表示できません。**
> この行で利用者情報がない場合にも `user.name` を読んでいるため、未ログインで開くとエラーになります。
> 利用者情報がない場合はログイン画面へ案内する分岐を追加してください。

## 進捗コメント

冒頭で重要な変化と影響を伝え、根拠・残件・必要な判断だけを続ける。
背景の再説明、空の見出し、定型的な「次のアクション」、未変更のバックログは省く。
短い更新は一段落でよく、概要と箇条書きで同じ成果を二度書かない。
完了は確認した範囲を明示し、「テスト成功」だけで完了・利用者承認・本番反映を推定しない。

架空の前後例（実投稿では実際の根拠に置き換える）：

- **連投の改善**：「調査開始」「修正済み」「テスト成功」を3コメントにしない。
  引き渡し時に「再送信しても申込みが重複しない修正ができました。再試行のテストは成功しています。
  実環境での確認をお願いします（PR #125）」とまとめる。PRに既に同じ引き渡しがあればIssueへの追記は省く。
- **転載の改善**：PR #125に修正・検証・残件が揃っている場合、個別Issue・親Issue・定例へ同文を貼らない。
  明示依頼された定例では、複数タスクに影響する変更だけをまとめ、必要なPRを参照する。
- **障害の記録**：「API依存でblocked」ではなく「申込みの保存先APIが利用できず、結合テストを進められません。
  復旧を待つか、テスト用APIで先に確認するか判断が必要です（前提作業 #124）」とする。
- **機能追加Issue**：「draft persistを実装」ではなく「入力途中の申込みを保存し、同じ利用者が後から再開できるようにする」。
  完了条件に「保存失敗時は保存済みと表示しない」「別の利用者は読み出せない」を残す。

## 関連する作業と次の行動

- IssueやPRのリンクには関係を添える。「対応する不具合」「先に必要な作業」「このPRでは未対応」など。
  同一リポジトリでは #番号、別リポジトリでは repo#番号かURLを用い、曖昧にしない。
- 完了・進行中・未対応を分ける。次の行動は「調整する」ではなく、何を確認／修正するかを書く。
  担当・期限は確認済みの場合だけ添え、不明なら補わない。
- Issueを閉じるキーワードは、本当にそのIssue全体を解決し、その扱いが依頼範囲に含まれる場合だけ使う。
  一部対応なら通常の関連リンクと残作業を記す。
- 文章を読みやすくする依頼だけで、親子関係・担当・期限・状態を変更しない。
  Issue本文を過去の説明ごと置き換えたり、同じ報告を複数の場所に重複投稿したりしない。

進捗報告の改善前：
> #123 applied、#124 pending。Status更新済み。

改善後（架空の進捗例）：
> 再読み込み後もログインを維持する修正を反映しました（対応PR：#125）。
> 残っているのは実ブラウザーでの確認です（確認作業：#124）。
> 次に、有効期限内と期限切れの両方で、期待した画面が表示されるか確認します。

依頼または合意済み運用に定例Issueへの追記が含まれる場合だけ、`planning-and-meetings.md` の手順も使う。
