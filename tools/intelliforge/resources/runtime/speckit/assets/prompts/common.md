新規の標準成果物はrequirements.md（要件）、design.md（設計）、verification.md（検証）の3文書です。
各文書は結論・確認してほしいこと・未確認を先に書き、関連する詳細を節にまとめます。文書の項目は固有のupstream:section内に置きます。
Researchを実行した場合は1本のreport.mdを参照し、採用理由を設計、確認条件と結果を検証へ戻します。報告の全文を複製しません。
既存の旧形式は明示したmigrateでだけ移行します。公式のspec.md/plan.md/tasks.mdは必要な詳細として保持します。
日本語の要件・設計・検証文書、研究・レビュー報告の下書きには、利用可能なyomiyasuを読んで一度推敲することを推奨します。
主張、専門用語、ID、数値、条件、確認結果、根拠、断定の強さ、upstreamメタデータ・リンク・引用を保持します。
レビュー・承認前に本文を仕上げ、承認済み本文の変更は通常の再レビュー手順へ戻します。固定済み資料・生ログは保持し、未導入でも執筆と文書確認を続けます。

このプロジェクトでは、全作業モードで共通の上流文書体系を維持してください。

最初に現在の目的・スコープ・関係者・既存仕様・設計・テストと、この依頼の対象を確認してください。
上流文書がない場合は調査計画から始め、分からない目的や合意事項を推測して確定しないでください。

整理順は、目的 → 関係者の要求 → 利用シナリオ/ストーリー → 検証可能な要件 → 仕様/設計 → 検証計画です。
上位と下位を一対一に押し込まず、多対多の関係を固有IDで表現してください。
非機能、インターフェース、データ、運用、制約を独立に検討してください。
現状の観測・過去の合意・改善案を区別し、根拠、対象版、確認日、不明点を残してください。

まず調査・整理計画を提示してください。承認後は文書作成・整理までを進め、
ソース変更、DB変更、破壊的テスト、本番アクセス、デプロイは別途明示承認があるまで行わないでください。
既存要件・方式の見直しで必要なresearch/auditは、依頼と既存の許可に含まれるローカル調査・隔離した検証/PoC・研究報告までを扱います。REASSESSMENT.mdに従い、アプリのソースや本番データは変更しません。
ECC・Basic Memory・既存Hook・AGENTS.mdは変更しないでください。

上流項目の合意は、文書を書いたこと自体では成立しません。
設定されたapproval profileに沿って `$upstream-review` でレビュー対象を固定し、
ユーザーが具体的IDを明示承認した場合だけ `$upstream-approve` でhash-bound approvalを記録してください。
レビュー後に本文や上位依存が変わった場合は古い承認を再利用せず、再レビューしてください。

要件・設計・検証の対応をupstreamメタデータに記録し、構造検査と対応表生成を行ってください。
構造検査の成功、ユーザー合意、意味上の妥当性、実テスト成功は別として報告してください。


## 文書の確認条件
- 全体READYを主張する前に、目的・ニーズ・ストーリー・要件・設計・検証計画の範囲があるか確認する。
- need/storyが本当に対象外なら、架空の要求を作らず、TRACE_FORMAT.mdのreadiness_exemptionsに従いgoalへ具体的な省略理由を記載してユーザーの合意を取る。
- 通常のMarkdown本文も承認対象に含まれる。明示した節はその節の項目に、節外の共通条件は文書内の全項目に結び付く。旧形式の節のない文書は文書全体を固定する。
- 旧版の承認は自動移行しない。新しいレビュー資料を提示し、ユーザーが承認した対象だけ再承認する。

## 設計前の必須研究・初見向け説明

`共通資材のreferences/RESEARCH_FIRST.md`を読み、次の順を守る。
**ユーザーストーリー → 未解決の懸念の確認 → 使用感を考慮したユースケース → 検証可能な要件 → 必要能力とコアロジックの切り出し → テーマ別design-research → 組合せ検証 → design.md → 検証計画**。
既に回答のある懸念は再質問しない。回答のない重要な前提を推測で確定せず、仮説と合意を分ける。
新規/変更の実現方式を設計する場合、design-researchの使用は任意ではなく必須。対象の判断だけを精緻に比較し、単純なAs-Is転記や誤字修正に全体再研究を要求しない。
現行要件正本を`--requirements`で固定し、`--reader-friendly`を指定して実際のresearchまたはreassessを使う。
要件変更時は前回の完了研究と新要件からreassessを開始し、別原理の案も実験可能にする。
研究不能なら方式確定を止め、理由を報告する。自動インストール、権限拡張、アプリ本体の変更は禁止。

設計文書は目的/例/用語→全体アーキテクチャ→重要コンポーネント詳細→代表処理→フレームワーク/実装詳細の順に説明する。
各図にキャプション・読み方・矢印の意味を添え、全体図のどこを詳細図で拡大したか明示する。
新規/方式変更のdesign.mdにはupstream-design-contract:v2のmarkerと、研究run・正本要件・図解・UI/UX適用記録を含むbindingを追加する。
約5方式の比較、採用理由と限界をdesign.mdへ戻し、実行固有のreport.mdを参照する。研究全文は複製しない。
画面例は実在するooui-design等のUI/UX Skillを必ず適用し、主要/空/処理中/失敗/復帰の該当状態を説明する。
静止画の見栄えを実操作や使いやすさの実測と混同しない。設計依頼からアプリ実装や修正ハーネスへ進まない。
すべての要件・設計・検証文書に目的と読み方、具体例、図の意味、用語、未確認を含め、承認前に初見の読者の立場で読み直す。

## 要件駆動の研究分解（全体を丸投げしない）
`共通資材のreferences/RESEARCH_WORKSTREAMS.md`を必ず読む。
要件から能力と不確実な計算/判断処理を逆算し、研究テーマ・要件ID・検証指標・入出力・依存関係を計画へ固定する。
画面/API単位では分けず、標準実装・要確認・対象外も理由付きで分類する。共通ロジックはまとめる。
約5手法は各テーマの比較目安であり、テーマ数を5に固定する意味ではない。
テーマごとに--workstream-plan/--workstream-idを付けてresearch/reassessし、独立コピーを使える場合だけ並列候補とする。
共通projectのロックは残す。親だけが全体文書を更新する。研究上の依存とアプリ実行順は別に定める。
最後に接続条件・組合せの品質/時間/資源を確認し、全体構成と各テーマの詳細を段階的に説明する。
v2 bindingに研究計画・テーマ別run・標準設計の根拠・統合評価の状態を残す。未実行を合格にしない。

## 研究との接続: ユーザーにSkillの使い分けを求めない
upstreamは全体ワークフロー（ストーリー→要件→方式比較→設計→検証）の親。
技術選択の不確実な部分を要件から切り出して、内部で `design-research` を実行する。
ユーザーは `$upstream-new` や `$upstream-change` でシステム全体の目的を伝えるだけでよい。
設計前には実行済みの研究結果と要件IDを接続し、統合後の設計・図解・検証を戻す。
必要な場合だけ `design-research/references/workflow-guide.md` の中の工程を選ぶ。
ユーザーに `design-research-plan` 等の旧ショートカットを使い分けさせない。
個別の研究は `$design-research` だけで依頼できる。計画と実験の結果を混同しない。
