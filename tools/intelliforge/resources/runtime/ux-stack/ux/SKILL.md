# UXの相談から設計・実装・確認まで進める

利用者が何を達成したいかと現在の問題を読み、必要な工程を組み合わせて作業する。
利用者に専門Skillや内部工程を選ばせず、Skill名を案内しただけで終了しない。
既存の仕様、実装、デザインシステムと今回の依頼範囲を優先する。

## 目的と反映範囲を判断する

対象アプリ、利用者、達成条件、既存資料、起動・検証方法を確認する。
環境や会話から分かることを質問し直さず、判断できない重要な一点だけ確認する。
「使いにくい点と改善案を教えて」は分析と提案まで、「改善して」は依頼範囲の実装と確認まで進める。
「設計まで」は実装を開始しない。「ファイル変更なし」は対話上の提案に留め、成果物も保存しない。

**工程の選択と、何を変更できるかを分けて考える。**
レビューでも原因が画面構造や導線にあれば、対象・操作を整理し、再設計案を検討する。
提案のためにコードや承認済みの設計契約を変更しない。現状と案を区別し、必要なら図やワイヤーフレームで比較する。
指摘だけの依頼では大きな設計成果物を付け足さず、図の存在だけで改善の効果を認定しない。

## 必要な専門手順を使う

下表は固定の分岐ではない。同じ依頼で観察、構造分析、再設計、実装、再確認を組み合わせられる。
必要なSkillを利用可能な一覧から名前で解決し、**実際の配置先のSKILL.mdを読んで**その手順を実施する。
隣接ディレクトリや絶対パスを仮定せず、全Skillと参照資料を最初から一括で読み込まない。

| 必要な工程 | 使う手順 |
| --- | --- |
| 新規UI、画面構造、導線の原因分析と見直し | `ooui-design`で対象・操作・画面・状態と認知負荷を整理する。既存アプリは実画面を先に観察する |
| 導線図、ワイヤーフレーム、再設計案、人が編集した図の取り込み | `ux-visual-design`。既存の設計メモを引き継ぎ、レビュー中の案は現状・承認済み契約と分けて扱う |
| デザインと実装 | 利用可能なProduct Design／Build Web Apps等の該当手順へ、構造・必須機能・必要な状態を渡す |
| 実装済み画面の監査・改善と再確認 | `ux-gan-harness`の実Bashハーネスを使う。評価は`audit`、修正を依頼済みなら`run`。所見を必要な構造分析・再設計にも渡す |
| UIコード、アクセシビリティの確認 | 必要に応じて`web-design-guidelines`。コード確認だけで実操作を検証済みにしない |

小さな文言・CSS修正では該当箇所を変更し、影響する表示・操作だけ確認する。
設計契約一式や全体監査を要求しない。ハーネスで局所確認する場合は既存のfocused手順を使う。
新規実装は必要なブラウザー確認まで行い、画像付きの監査・修正反復が必要な場合はハーネスへつなぐ。

## 引き継ぎと完了

目的、対象、観察結果と画像、設計メモ、画面・操作・状態、設計契約、未決事項を次の工程へ渡す。
既に読んだ関連資料・過去の指摘・推敲結果を再利用し、同じ質問、調査、モデル化、文章推敲を繰り返さない。
観察と提案、実装と検証結果を区別し、確認できたことと残件を短く返す。
ハーネス内の修正・再確認を親側で二重実行せず、同じ実行IDの完了まで追う。便宜上の短い時間制限や、対象を狭めた別実行で代用しない。
必要な専門Skillや実行環境がなければその限界を示し、可能な作業を進める。外部MCPがなければ既存のローカル可視化を使う。
無断で外部ツールを登録・再設定せず、実行していないハーネスや人間の評価を成功として報告しない。

専門Skillを直接指定された場合はその手順を尊重し、共通入口へ呼び戻さない。
`UX_GAN_CHILD=1`の子実行では、渡された役割と範囲に従う。この入口を再実行せず、新しいハーネスも起動しない。
このSkillの導入・整備は、別アプリの作成・修正を許可しない。
