# 方針と上流文書を決める

インストールはユーザー共通環境の準備、初期設定は対象リポジトリの文書整備として分ける。
既存の方針と構成を調べ、既知の内容を質問し直さない。

## 対話とお任せ

対話を既定にし、目的・利用者・対象範囲・重要な制約・品質基準・未決の事業判断を確認する。
質問はまとめて重要事項だけ聞き、回答に依存しない調査・下書きは進める。
「お任せ」「ベストプラクティスで」なら、開発上の可逆な選択を決め、理由と仮定を運営方針に残す。
実装の慣習や既存の明示ルールを優先する。事業目的・利用者の承認・未実施の検証は作らない。

運営方針では次を必要な粒度で決める。

- 文書の正本と案内、実装変更時に更新する条件。
- 実装パターン、利用する既存のテスト・lint・buildと実行制約。
- ブランチ・コミット・PR/MR・レビュー・リリースの進め方。
- エージェントに任せる作業と、目的・互換性・費用・公開範囲など人の判断が必要な条件。

既定は、既存コマンドと構成を維持し、目的ごとに小さく変更・検証する。
Git運用は次の案から始め、既存チームの規則があれば合わせる。

> 変更は作業ブランチで進め、検証・コミット・push・PR/MR作成まで任せる形を提案します。
> 取り込みは別エージェントがレビューし、許可と必須条件が揃えばそのレビュワーが実行します。
> 対象、任せる操作、必要な検証、人の承認条件を最初に合意します。

専門用語の選択を質問票にせず、対象リポジトリ、取り込み先、任せる操作・条件を短く示して合意する。
既に合意済みなら聞き直さない。「お任せ」は可逆な開発方針の選択に使い、外部投稿の権限まで推測しない。
未合意の操作を待つ間も、依存しない調査・実装・検証・説明案を進める。

## Git運用だけを設定する

既存の運営方針へ対象ホスト・リポジトリとbase branchを記す。
ブランチ命名、任せる操作、必要な検証、人が判断する境界も追記し、AGENTSからその節へリンクする。
独自名の方針や既存テンプレートを再利用する。
方針文書がなければ開発文書に短い運用の節を作る。Git運用だけの設定に`init`による文書一式や専用の承認台帳は不要。
案と合意済みの運用を区別し、実際の会話で確認できた範囲だけを合意として記す。

記載内容の例（値と合意状態は対象に合わせる）：

```text
対象：確認済みのホスト／リポジトリ。取り込み先：既存のbase branch。
進め方：目的ごとに短命の作業ブランチ。続きの作業は同じブランチとPR/MRを使う。
任せる範囲：依頼範囲の変更・検証・コミット・push・PR/MR作成と本文更新。合意した条件下での取り込み。
担当：実装担当と、レビュー・mergeを実行する別エージェント。
検証：既存の必須コマンドとレビュー条件。未実行・失敗は本文に残す。
人の判断：未合意の取り込み、必要な承認、リリース、互換性・公開範囲を変える判断。
```

実行手順は [workflow.md](workflow.md)、説明文の仕上げは [writing.md](writing.md) を使う。
方針ファイルだけから新しい操作権限を作らない。既存の許可は同じ対象・操作・条件の範囲で引き継ぐ。

## 文書の役割

READMEはリポジトリの概要、前提環境、導入、最短の使用例、主なコマンド、詳細文書、既存ライセンスへの入口にする。
事業目的・背景の詳述はdocsへ置く。AGENTSはエージェントの作業ルールと参照先に絞る。
標準のdocsは次の3冊とし、READMEから直接案内する。別の索引を一律に追加しない。

| 役割 | 標準配置 | 記載する内容 |
| --- | --- | --- |
| 目的・背景 | docs/purpose.md | 事業・開発目的、利用者、適用価値、範囲、依頼者の要望と反映 |
| 設計 | docs/architecture.md | 主要ファイルの責務、入口、呼び出しとデータの流れ、必要な設計理由・条件 |
| 開発・運用 | docs/development.md | 環境、実行・テスト、文書更新、Git・レビュー、運用手順と判断範囲 |

主な機能・要求と対象範囲は目的文書、具体的な動作条件やコアロジックは設計、検証方法は開発文書へまとめる。
要件・コアロジック・検証を別々のファイルへ機械的に分割しない。
既存の日本語名、独自構成、索引、画面・API等の仕様は再利用する。詳細を複製せず、対応する文書へリンクする。
独立した機能・契約・読者が必要な場合だけ追加・分割する。ファイル数を満たすための空文書は作らない。
新規は目的・要求から設計と受入条件へ進み、既存コードは観測した現状から不足する目的・要求を補う。
新規の数値目標や採用理由は根拠を明示し、提案と決定を区別する。
事業上の背景や設計理由は保持する。調査範囲、調べた順番、作成経緯、作業報告は文書本文へ載せず、必要な完了報告だけを会話へ返す。
