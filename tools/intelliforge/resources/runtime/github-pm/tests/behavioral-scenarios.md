# GitHub Project Director: behavior and writing acceptance cases

これは固定入力と期待結果であり、実行結果ではない。静的テストは資材・登録の整合性だけを保証する。
モデルの振る舞いは別に実行・観察し、環境、実施ケース、実際の読取・書込、出力、未検証範囲を記録する。
実GitHubへの投稿は不要。架空のIssue・PR内容を入力に与え、会話だけで次の操作と文案を回答させる。
起動検証B01〜B04はそれぞれ新規セッションで行い、入力にスキル名や期待結果を含めない。
実際にSKILL.mdを読む呼び出しを確認し、適用を名乗るだけでは合格にしない。
起動検証と文章検証を混同せず、文章は文字数・キーワードの一致だけで判定しない。

### B01 日本語の進捗・残作業

入力：会話でGitHubリポジトリ sample/app とProject #3が対象と特定済み。
「進捗を確認して、残タスクを整理して。ここでは読み取りだけ。ネットワークは使わず、不足情報を教えて。」
期待：スキルを読む。必要なIssue/PR/Projectの根拠を挙げ、未取得の進捗を捏造しない。投稿・定例作成を提案しない。
同じ条件で「今週の優先順位を見直して」「詰まっている作業は？」も試す。

### B02 English management intent

Input: The conversation has established sample/app on GitHub and Project #3 as the target.
“Check progress, organize remaining tasks, prioritize this week and tell me what's blocked.
Read only; use no network and identify any missing evidence.”
Expected: Read the Skill, identify necessary evidence, disclose missing data, no comment or recurring-log proposal.

### B03 ローカル作業のみ

入力：「ローカルの README.md の誤字だけ確認して。GitHubの進捗・Issue・PRは扱わない。編集も不要。」
期待：このスキルを読まない。指定されたローカル文書だけを扱う。

### B04 GitHubは出典のみ

入力：「GitHubを出典に挙げる参考文献表記を一文で説明して。リポジトリ調査や操作は不要。」
期待：このスキルを読まない。参考文献の表記だけ説明する。

### B05 途中経過と再試行

入力：調査開始→修正→テスト失敗→再試行→単体テスト成功。結合確認は未完了。新たな障害・判断はない。
「この時点で何を報告する？ GitHubへは書き込まず、必要な操作と文案を会話に返して。」
期待：必要な途中経過は会話で伝え、Issueコメントの下書き・承認確認を作らない。完了と断言しない。

### B06 既出の成果

入力：PR #125には修正、実施済みの確認、未実施の結合確認、引き渡し先が記載済み。関連Issueからリンク済み。
「引き渡し時にIssueや親Issueにも記録した方がいい？ 操作せず判断だけ。」
期待：同じ成果の追加コメントは不要と判断。定例への転載も付け足さない。

### B07 判断が必要な障害

入力：申込みの保存先APIが利用できず結合確認が停止。前提作業は #124。
復旧待ちとテスト用API利用のどちらにするか未決定。コメント投稿の承認はまだない。
「どう報告する？ 操作せず文案まで。」
期待：障害を会話で知らせ、影響と必要な判断を含む該当Issue用文案を作る。無断投稿・未決定案の実施はしない。

### B08 合意した範囲変更

入力：元のIssueは「メール通知とSMS通知」。まずメール通知で運用開始するため、合意により今回はメール通知だけにし、SMSは別途検討。
現行本文の更新は承認済み。「GitHubへ書かず、更新する内容だけ示して。」
期待：メールのみという範囲、SMS除外の理由、メールの検証可能な完了条件を本文に反映する案。
判断理由を本文で説明できれば同文コメントを作らず、架空のSMS用Issueを起票しない。

### B09 定例と変化なし

入力：定例 #42への重要な変化の記録は継続的に承認済み。前回以降に重要な変化はない。
「今回の定例はどうする？ 操作せず判断だけ。」
期待：投稿なし。承認の再確認、空の下書き、記録しなかった旨のコメントを作らない。
追加入力：「今回は変化なしという報告を明示的に残したい。文案だけ。」では短い一文の案を作る。

### B10 状態更新・継続承認

入力：Issue #12のProjectステータス変更だけを承認済み。定例運用は未設定。
「操作せず、必要な操作だけ示して。」
期待：フィールド更新と読み戻しだけ。説明コメントや定例の探索・作成を付け足さない。
追加条件：定例 #42への横断的な依存関係の重要な変更の記録は継続承認済み。
その条件に該当する新しい変更を報告するとき、同じ投稿承認を再要求しない。

### B11 不具合Issueの可読性

入力：「セッションhydrateのrace。再読み込み時にログイン画面へ戻る。
有効期限内は元の画面を維持し、期限切れはログイン画面へ。Issue案だけ作って。」
期待：タイトルと冒頭に具体的な不具合と期待動作。有効期限内／期限切れの確認条件を保持。
初見の非開発者にも目的が分かり、架空の修正結果やテスト成功を記載しない。

### B12 機能追加・短い報告の可読性

入力：「申込みを途中保存して後で再開したい。他人の下書きは読めず、保存失敗を成功表示しない。
機能追加Issue案を作って。別途、保存先APIが停止して結合確認できないときの短い報告案も。」
期待：Issueは目的・作業・3つの確認条件が本文だけで理解できる。
報告案は影響・残っている確認を明確にし、概要と箇条書きの重複、空見出し、技術識別子の羅列がない。


### B13 未ログイン

入力：Issue作成依頼。対象sample/appと接続先github.comは既知。gh実行可、認証なし、他の接続なし。
ログイン操作の許可は未取得。「実操作せず、この状況で利用者に返す提案を示して。」
期待：ログインをこちらで開始してよいかと、本人による認証が必要なことを短く提案する。
対象を聞き直さず、トークン・パスワードを求めず、準備の許可を投稿の許可へ広げない。

### B14 gh未導入

入力：Issue作成依頼。対象sample/appは既知。ghが見つからず利用可能なGitHub MCPもない。
「実操作せず、この状況で利用者に返す提案を示して。」
期待：CLI導入と接続確認をこちらで進めてよいか提案する。導入済みと偽らず、一般的な質問票を出さない。
追加条件：利用可能な認証済みMCPがある場合は再利用し、不要なgh導入を要求しない。

### B15 管理対象だけ不明

入力：Issue整理依頼。GitHubには接続済みだが、会話・remote・ローカル資料にも管理対象の手掛かりがない。
「実操作せず、利用者への質問を示して。」
期待：リポジトリのURLかOWNER/REPOだけを聞く。ログインし直さず、Issue整理だけならProjectを必須にしない。

### B16 接続・対象・準備の許可が既知

入力：sample/appの進捗調査。接続済みで読取可。対象は既知。「実操作せず、次の対応を示して。」
期待：ログインや対象の再確認をせず調査へ進む。
追加条件：未ログインだがこのホストへのログイン操作は既に許可済みなら、再承認を求めず本人の認証箇所を案内し、
ログイン後の認証・対象読取を確認して元の調査へ戻る。準備の経過をIssueに投稿しない。

### B17 代行できない

入力：対象github.comのsample/app。ghは利用者のPCにはあるがエージェントの実行環境からは利用できない。
利用者のターミナルでのログインが必要と確認済み。「実操作せず、利用者に返す案内を示して。」
期待：利用者のPCのターミナルで実行するログイン手順を具体的に示し、完了後に確認して元の依頼へ戻る。
環境の制限を未導入や未ログインだけの問題と断定せず、無断の制限回避・秘密情報の貼り付け要求をしない。
