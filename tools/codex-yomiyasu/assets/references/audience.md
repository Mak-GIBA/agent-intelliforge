# 指示者への返答を完成稿に残さない

## 文の宛先と機能で判断する

読者が必要とする対象の説明と、依頼者への作業報告を分ける。「なぜ書き手がこう書いたか」だけを説明する文は通常、本文に不要である。文書を理解するために必要な研究目的・対象範囲・用語定義・実験方法・節の案内は別であり、残す。

対象範囲は本文だけでなくタイトル、リード、見出し、キャプション、表、脚注、代替テキスト、末尾である。「図1：初見の人にも分かるように作成した構成図」は「図1：システム構成」へ直す。ただし具体的なシステム名や機能を原文になければ補わない。

## 削るか、移すか、言い換えるか

「ご依頼のとおり、方式AとBを比較した」は、文書に必要な比較事実があれば「方式AとBを比較した」とする。「読みやすさを重視して構成した」は削る。「日付は未指定なので仮置きした」は、確定値を捏造せず、納品時の確認事項へ移す。

研究上の未検証、仕様上の未決定、意思決定を変える条件は読者に必要な情報なので残す。「研究データが不足しています」と「この原稿の制作で資料をまだ取得していません」は、似ていても機能が異なる。原文で区別できなければ勝手に研究上の限界へ書き換えない。

悪い変更：
「必要なら追加実験もできます」→「追加実験を実施する必要がある」
「分かりやすくするため背景から説明します」→「従来手法は計算量が大きい」
どちらも、元になかった判断・事実を加えている。元の内容がない場合は、文自体を削除する。

## 保持する反例

メールの「添付資料をご確認ください」は受信者への正当な依頼なら残す。手順書の「設定を確認してください」は操作内容として残す。AI技術の説明にある「プロンプト」は技術用語なので残す。査読回答の「ご指摘に基づき図3を修正しました」は、その文書の読者に伝えるべき回答であり、チャット混入ではない。

小説・インタビュー・引用・プロンプト教材の例文は内容として保護する。テンプレートの「[担当者名]」、画面の「要確認」ステータス、開発ドキュメントのTODO実装例を、未完成と即断しない。逆に、完成稿に残ったHTMLコメントの編集指示は公開時に見えなくても点検する。

## 出力の分離

完成稿ファイルには完成稿だけを保存する。作業報告や検査JSONを見出しで分けて同じファイルに追記する運用は避ける。ユーザーが制作手順の解説や編集履歴を成果物として求めたときは、その文書の内容として含めてよい。

## 同じ文言でも宛先を分ける

「あなた」「ご依頼」「ご確認ください」の文字列ではなく、誰への何の連絡かで判断する。

| 文の役割 | 扱い |
|---|---|
| 完成稿の読者が理解・判断・実行するための事実、定義、条件 | 本文に残す |
| AIに与えた文体、構成、分量の指示と、その実施報告 | 本文に書かず、文章の作り方に反映する |
| メールの実際の受信者への依頼、査読者への修正回答 | 文書の内容として残す |
| 引用、コード、プロンプト教材、依頼された編集履歴 | 内容として保護する |
| 制作上の未確認と研究・仕様上の未確定の区別が不明 | 勝手に確定・一般化せず、必要な確認を本文外に分ける |

混在文は情報の単位で分ける。「ご指示どおりREQ-12の保存期間を90日と記載した」では、REQ-12と90日の内容は保持し、指示への応答だけを除く。制作コメントを丸ごと消して唯一の事実も失う変更は避ける。

本文をプロンプトと会話履歴から切り離して読む。「前述のご希望」「このように直しました」が何を指すか読者には分からない場合、制作上の説明は除く。定義や比較条件が不足している場合は、手元の素材にある情報で補い、無ければ創作しない。指示者と読者が同じ人でも、完成稿に必要なのは対象の説明である。
