# 2.0.0-proposal.2の比較契約

実験の生成・採点は明示実行専用。インストーラー、通常のスキル利用、自己テストはモデルを呼ばない。

## 比較条件

現行2.0.0-proposal.1を変更前に保存し、A（連携と点検）、B（A＋執筆前の読者・素材分離）、C（A＋下書き後の読者視点レビュー）を作る。上流原本は全条件で同じインストール済みスナップショットを使う。約5案という研究スキルの標準に対し、今回はユーザーの指定した改善3案と基準案の4条件を比較する。

文章生成は既存12課題×4条件×2回＝96試行。原稿・素材、保持すべき意味、採点基準、モデル、reasoning、規則のハッシュを生成前に固定する。生成順はseed 20261011で入れ替える。1出力1セッションとし、全規則を入力に展開する。この比較だけで実際のスキル自動選択や参照取得を証明しない。

ネイティブ試験は8依頼×4条件＝32試行。全体の明示・暗黙起動、段落だけと留保だけの明示・暗黙起動、誤字だけ、コードだけを使う。候補の3スキルを一時プロジェクトへ正式なインストーラーで導入する。既存のユーザー設定・rulesを読み込まず、AGENTSの追加読込を無効にし、既存ローカルスキルをCLI設定で無効にする。これらの経路だけを試験用の重複検出から除外し、本番インストーラーの保護は変えない。読込の判定は成功した実ファイルの読取コマンドと返されたSKILL本文を確認し、名前への言及だけでは合格にしない。

採用前に、比較に使わない新規6課題を固定する。選定後、現行版と採用候補で各1回＝12完成稿を生成し、意味保持と読者境界を再確認する。

## 評価と採用

採点者へ条件名・規則・実行時間を渡さず、原稿／素材と完成稿だけを匿名で提示する。生成と同じモデルを別セッションで使う自動評価であり、人間評価ではない。重大な意味変更、正当な宛先への依頼・引用・コード・数式の破壊、判定が割れた箇所は親が実際の入出力で再確認する。

原契約の主要指標は、取得できた完成稿のうち、意味変更0件・制作コメント混入0件・段落／自然さ／読者適合が各3点以上（0〜4）の割合。全試行を分母にした取得・合格率は`delivered_pass_fraction`として別記する。数値、否定、条件、主体、因果、時間、確信度、義務と推奨を保護する。制作コメントの削除や意味を保つ言い換えを情報脱落と数えない。

重大な意味変更または正常例の破壊がある案は採用しない。連携が成立する候補の中で主要指標、混入の少なさ、品質平均、所要時間・報告トークンの順で選ぶ。同率を品質改善の証拠としない。全案不合格なら新版を採用しない。

所要時間は起動から完成稿まで。各工程のworkerは2で、工程が重なり最大6要求が動いたため、時間は負荷を統制した比較値ではない。トークンはCLIが報告したusageを使い、料金の節約に換算しない。CLIで制御できない温度等は未制御と記録する。480秒の試行上限、1800秒の研究工程上限を維持する。失敗・タイムアウトを保存し、自動再試行しない。完了したreceiptのハッシュを照合して再利用する。

最初の手動コピーによるネイティブ事前確認は管理manifest不足で不適切だった。`native-setup-invalid`に保持し、32試行の比較から除外する。実装・環境修正後の試行と混ぜない。

## 再現

保存済みの試行を再生成せず照合する場合は、`audit_study.py`を使う。96件の生成入力と12件の追加確認入力のハッシュ、匿名採点からの集計、32件の実ファイル読込、配布資材と比較したC案の一致を検査する。版番号と由来情報の更新は本文の変更と分けて記録する。

実機入力の復元文、原receiptのハッシュ、依頼範囲と読込証拠、読込なしの対照を併せて検査する補足は、次のコマンドで再現できる。32件は照合したreceipt数であり、全文読込があった試行数とは分ける。独立レビューでの指摘と研究の中断は[検証記録](../../../docs/codex-yomiyasu/validation.md)を参照する。

```bash
python3 -B docs/codex-yomiyasu/evidence/study-2026-10-11/native_provenance_audit.py
```

```bash
python3 tools/codex-yomiyasu/evals/audit_study.py \
  --out docs/codex-yomiyasu/evidence/study-2026-10-11 \
  --sources tools/codex-yomiyasu/evaluation-v200 \
  --upstream-dir /path/to/installed/yomiyasu/upstream \
  --final-assets-dir tools/codex-yomiyasu/evaluation-explanation/snapshots/baseline/assets
```

```bash
python3 tools/codex-yomiyasu/evals/build_candidates.py --out /path/to/new-sources
python3 tools/codex-yomiyasu/evals/run_study.py prepare \
  --out /path/to/new-study --sources /path/to/new-sources \
  --upstream-dir /path/to/installed/yomiyasu/upstream
python3 tools/codex-yomiyasu/evals/run_study.py writing --out /path/to/new-study
python3 tools/codex-yomiyasu/evals/run_study.py native --out /path/to/new-study
python3 tools/codex-yomiyasu/evals/run_study.py grade --out /path/to/new-study
```

`build_candidates.py`はリポジトリでは保存済みのproposal.1原本を基準に比較を再構成する。別の基準には`--baseline-assets`を指定する。今回の変更前の原本と候補は`evaluation-v200`、規則と上流の固定ハッシュは証拠の`contract.json`に保存する。旧1.1/1.2比較と今回の比較を同一の成果として扱わない。認証と内部思考の逐語記録を証拠へ含めない。

12完成稿単位の採点工程2件が時間上限に達したため、未評定分は新しい4完成稿以下の工程へ分割した。旧工程の再投入や、完了した採点の繰り返しは行わない。`grade_remaining.py`のmanifestと元の失敗receiptを併せて保存する。採点文脈の大きさが一様でないことは限界として報告する。

初回の固定ハッシュには生成済み`__pycache__/*.pyc`が4条件に含まれていた。これらは規則の入力にも配布物にも含めていないため、再現時の固定ハッシュ照合から除外する。元の契約は改変せず保存し、今後の候補構築ではキャッシュをコピーしない。

採用時の実装ゲートは24稿全ての取得・採点を要求している。これは`contract.json`の品質指標・選択文より厳しい保守的な追加条件であり、事前の品質比較とは区別する。全条件の取得済み完成稿は100%合格で、Cの文体上の優位性は未確認。ハーネス用に先に固定した捕捉の`primary_fraction`は全試行を分母にしており、その名前では原契約に一致しない。最終集計では原契約に従う品質率と取得率を分離し、元の捕捉は改変しない。

研究の`prepare`だけは設定のTOML読込にPython 3.11+を使う。通常の導入・展開・自己テストのPython 3.10+要件は変えない。実機記録の再照合は、`verify_native.py --out <証拠ディレクトリ> --sources <固定済み4条件>`で行う。プロンプトのハッシュ、期待経路、実際の読取コマンド、返されたSKILL全文を照合する。私的な推論内で何回適用したかは観測できない。
