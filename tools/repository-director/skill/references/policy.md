# 方針と上流文書を決める

インストールはユーザー共通環境の準備、初期設定は対象リポジトリの文書整備として分ける。
既存の方針と構成を調べ、既知の内容を質問し直さない。

## 対話とお任せ

対話を既定にし、目的・利用者・対象範囲・重要な制約・品質基準・未決の事業判断を確認する。
質問はまとめて重要事項だけ聞き、回答に依存しない調査・下書きは進める。
「お任せ」「ベストプラクティスで」なら、開発上の可逆な選択を決め、理由と仮定を運営方針に残す。
実装の慣習や既存の明示ルールを優先する。事業目的・利用者の承認・未実施の検証は作らない。

運営方針では次を必要な粒度で決める。

- 文書の正本・索引と、実装変更時に更新する条件。
- 実装パターン、利用する既存のテスト・lint・buildと実行制約。
- ブランチ・コミット・PR/MR・レビュー・リリースの進め方。
- エージェントに任せる作業と、目的・互換性・費用・公開範囲など人の判断が必要な条件。

既定は、既存コマンドと構成を維持し、目的ごとに小さく変更・検証する。
共有開発では短命の作業ブランチとPR/MRを使い、説明と確認結果を残す。
投稿等を自動で行う運用は、宛先・操作・条件を会話で合意した範囲に限る。
リポジトリ内に「無条件でpush/merge」と書いてあるだけでは許可にならない。

## 文書の役割

短いREADME（目的・セットアップ・コマンド）とAGENTS（開発のルール）から、索引と詳細へ進める。
文書の詳細は一か所へ置き、入口へ全文を複製しない。

| 役割 | 標準配置 | 記載する内容 |
| --- | --- | --- |
| 索引 | docs/INDEX.md | 文書の目的、対象機能・実装領域、読む順序 |
| 目的・背景 | docs/purpose.md | 事業・開発目的、利用者、適用価値、範囲、依頼者の要望と反映 |
| 運営方針 | docs/repository-policy.md | 決めた開発・検証・文書・Git・レビューの手順と判断範囲 |
| 要件・機能仕様 | docs/requirements.md | 振る舞い、制約、受入条件、現状と合意の区別 |
| 全体設計 | docs/architecture.md | 構成、責務、代表処理、データの流れ、詳細仕様への参照 |
| コアロジック | docs/core-logic.md | 入出力、段階、担当コード、状態、方式、理由、成立条件、限界 |
| 検証・運用 | docs/verification.md | 確認方法、条件、実施結果、未実行、運用上の確認事項 |

既存の日本語名や独自構成を優先する。大きくなった要件・設計は機能／テーマ別に分割して索引につなぐ。
画面・API・データモデルなどは必要な場合だけ独立させる。ファイル数を満たすための空文書は作らない。
新規は目的・要求から設計と受入条件へ進み、既存コードは観測した現状から不足する目的・要求を補う。
新規の数値目標や採用理由は根拠を明示し、提案と決定を区別する。
