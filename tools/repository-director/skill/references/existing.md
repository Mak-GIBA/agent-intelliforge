# 既存コードから文書と開発ガイドを整える

「このコードの仕様書とAGENTSを整えて」「既存プロジェクトを引き継げる資料にして」で使う。
調査・本文作成・入口整備までが成果。雛形の配置、ファイル一覧、実装の逐語説明だけで終了しない。

## 対象を読み解く

既存のAGENTS/README、索引、仕様、依存定義、実装入口、主要モジュール、テスト、CI、運用資料を調べる。
まず全体像と機能・モジュールの関係を把握し、依頼範囲と重要な処理から詳細を追う。
モノレポは親の方針を尊重し、対象パッケージ外を勝手に整備しない。
コードだけ、資料が一部だけ、名称が独自、英語資料、実行環境なしでも開始できる。
調査できたコード版と範囲を記載する。本番の状態が同じかはアクセスなしに断定しない。
設定は名前と用途だけ。環境ファイル・認証情報・実データの値を複製しない。

主要な操作を入口から、認証・検証・コア処理・保存・応答まで追う。
画面の存在を操作権限の証拠にせず、似たAPIから権限や応答を推測しない。
テストは何を確認するかと実行済み結果を分ける。依存を用意できなければ静的調査と未実行を明示する。
文書整備のためだけに依存更新・破壊的テスト・本番アクセスを始めない。

## 文書の担当を決める

[policy.md](policy.md)の役割に、既存文書を先に対応付ける。
LISTBOX型の「短いREADME/AGENTS → 索引 → 用途別仕様」を基本とするが、ファイル名は固定しない。
既存の画面・API・データ・テスト仕様は活用し、別の新規文書へ全文を複製しない。
既存資料を読まずにinitを実行しない。独自名の正本には `init --document <role>=<relative.md>` を使って対応を指定できる。
不足する事業目的やコアロジックの説明を補う。画面のないプロジェクトに画面仕様を作らない。

各文書は対象範囲、具体的な内容、根拠となるコード・テスト、未確認事項を読める状態にする。
現状、正式な要件、変更提案を分け、既存文書と実装が矛盾する場合は双方の根拠と差を残す。
今の不具合・不十分な権限チェックを「意図した仕様」と追認しない。
業務目的・採用理由がコードにない場合は依頼者や過去資料を確認し、根拠がなければ未確認と書く。

依頼者のコメントは要望・背景・理由、採用／不採用／保留、反映する要件、必要な出典を整理する。
発言の要約を承認と扱わない。会話全体や作業日誌を蓄積しない。

## AGENTS・README・索引を仕上げる

- README：何のためのものか、始め方、使うコマンド、仕様・開発ガイドへのリンク。
- AGENTS：実装の入口、関連仕様の確認、変更と検証のルール。詳細は正本へリンクする。
- 索引：各文書の内容・対象領域を短く示し、必要な資料を選べるようにする。
- CLAUDEを使う場合：共通方針をAGENTSへつなぎ、ホストごとに仕様の正本を複製しない。

既存の説明・ユーザー編集・独自ルールを保持し、今回の対象に必要な箇所だけ統合する。
既存の題名と見出し階層を生かし、一つの文書に新たな最上位見出しを並べて追加しない。
AGENTSは作業の入口と守るルールに絞り、詳しい目的・仕様・判断理由は対応する正本へリンクする。
ヘルパーが作る「調査用の下書き」は実調査で埋め、未確認を残す場合は具体的な対象を書く。
文書が現状を説明していても業務上の合意とは別であることを保つ。

最後にリンク・内容・参照先を照合し、変更が管理文書に限定されているか確認する。
コード・依存定義・ロックファイル・DBは変更しない。発見した問題は改善候補として返す。
再実行は不足と変化だけを補い、既存の索引や節を重複生成しない。
