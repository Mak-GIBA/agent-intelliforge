# 既存コードから開発者向けの文書を整える

初めて読む開発者が、事業上の目的、処理の入口、実装の担当箇所を理解できる文書を作る。
既存資料とコードを読み、本文とREADME・AGENTSの導線まで仕上げる。

## 目的と実装を読み解く

既存のAGENTS/README、目的・要件・設計、依存定義、起動設定、実装、テストを確認する。
事業目的・背景・利用者は依頼や資料を根拠にする。コードだけから事業上の意図や合意を作らない。
必要な目的が不明なら重要な一点を確認し、回答に依存しない実装の確認は進める。
既存の説明と実装が食い違う場合は差を確認し、不具合を正式な仕様として追認しない。

起動コマンド、公開API、画面操作、定期処理等の入口から、振り分け、処理本体、保存・外部連携、応答まで追う。
importや似た関数名だけで呼び出しを断定せず、実際の呼び出しや登録を読む。
権限、分岐、非同期処理、データ・状態は大枠の理解に必要なものを扱う。
設定は名前と用途だけを記し、認証情報や実データの値を複製しない。
モノレポは親の方針を守り、対象パッケージ外を勝手に整備しない。

## 3冊へまとめる

[policy.md](policy.md)の目的・設計・開発の3冊を基本とし、既存の正本と索引を先に対応付ける。
既存資料を読まずに`init`を実行しない。独自名の正本は`--document <role>=<relative.md>`で再利用できる。
主要機能は目的文書、具体的な動作とコアロジックは設計、テストと変更のルールは開発文書へまとめる。
目的文書は事業上の課題・利用者・価値・対象範囲を中心にし、細かな入力例や未決事項の羅列へ広げない。
既存の画面・API・データ等の仕様を別文書へ全文複製せず、必要な参照を残す。
独立した機能・契約・読者が必要な場合だけ分割する。

設計文書は次の順で書く。

1. **全体像**：何を受け取り、どの主要部分が処理し、何を返すかを生成画像と短い本文で説明する。
2. **ファイル構成**：主要ディレクトリとファイルの注釈付きツリーを載せ、各ファイルが担当する処理を示す。
   小さな補助ファイル、テスト、生成物は責務単位でまとめる。読んだファイルの一覧を代用にしない。
3. **エントリーポイント**：起動コマンドや操作・要求の契機と、入口のファイル・主要関数を対応付ける。
4. **主要処理の流れ**：入口からの呼び出しとデータの流れをMermaidで図解する。
   ノードに担当ファイルや主要関数を添え、本文で処理の目的と受け渡すデータを補う。
   多数の小関数をノードにせず、分岐や非同期の境界は理解に必要な範囲で示す。
5. **設計上の要点**：責務分担や方式の理由、成立条件と限界を必要な分だけ説明する。

全関数の説明や実装の逐行解説を作らない。まず大枠を続けて読める状態にし、詳細は担当コードや既存仕様へ案内する。
例外型、ライブラリの既定値、入力の全パターン、細かな並び順を列挙しない。利用や変更判断に必要な条件だけを主な処理の近くへ残す。
図の接続、実在するパスと主要関数、本文の動作を実コードと照合する。
事業背景・確認できた採用理由・重要な動作条件は省かず、提案と確認できた事実を区別する。
採用理由の根拠がなければ構成と影響を説明し、「採用経緯は不明」等の定型的な経緯説明を足さない。

## 図で理解の入口を作る

目的・背景・主要概念・全体像は、説明用の生成画像を中心にする。読者が対象や入力・処理・結果の関係をつかんでから、具体的な実装へ進めるようにする。
正確なパス・関数名・分岐は注釈付きツリーとMermaidへ、画面操作は実画面へ、計測結果はデータから作る図へ分担する。
生成した模式図を実画面や実測結果として使わず、図だけに重要な条件を閉じ込めない。

本文・実装と整合し、説明したい概念を示せる既存の図は再利用する。不足する図だけを利用可能な画像生成Skill・ツールで作り、小修正のたびに全図を作り直したり、各節に機械的に画像を増やしたりしない。
図は対象プロジェクト内の既存の資材配置に保存し、説明する本文の近くから相対参照する。新規ならdocsのassetsへまとめる。
代替テキストと短い説明を付け、模式図の省略や比率など、読み違えやすい条件だけを添える。

生成後は実際に表示し、文字・矢印・凡例・入力と出力を本文、コード、出典と照合する。未知の部品・呼び出し・値を創作しない。
実装や説明が変わったら関係する図も点検する。画像生成が利用できない場合は、文書本体を既存図・Mermaid等で仕上げ、未生成の図は会話へ示す。
新たなAPI・鍵・CLIを勝手に導入しない。生成ツールの制約や制作経緯は完成文書へ転記しない。

## READMEとAGENTSを仕上げる

- README：リポジトリの概要、主な機能、前提環境、導入、最短の使用例、主要コマンド、docsへのリンク、既存ライセンスへの参照。
  内容は実際のプロジェクトに合わせる。事業背景の詳述は目的文書へ置く。
- AGENTS：変更前に読む文書、開発のルール、変更と検証の手順。仕様や事業背景を複製しない。
- 既存の索引：必要な文書を選べる短い案内として再利用する。新しい索引を必須にしない。
- CLAUDEを使う場合：共通ルールをAGENTSへつなぐ。

既存本文・ユーザー編集・独自ルール・見出し階層を保持し、必要な箇所だけ統合する。
今回の文書整備だけに適用する禁止事項や試験環境の制約を、恒久的な開発ルールや運用手順として転記しない。
開発手順には対象リポジトリで使うコマンドを記す。今回だけのSkillの配置、一時パス、同梱されない補助ツールのコマンドを追加しない。
調査範囲、コードを読んだ順番、文書整備の経緯、作業完了報告を本文へ入れない。
動作や検証の重要な未確認事項は該当箇所へ短く残す。各節へ「未調査」「未確認」を繰り返して埋めない。
テストの存在と実行結果を区別し、文書整備のためだけに依存更新・破壊的テスト・本番アクセスを始めない。

ヘルパーは雛形と案内の配置だけを行う。本文を仕上げた文書からだけ`<!-- repository-director:draft -->`を外す。
旧形式の下書き文言も完成時に取り除く。マーカーを外しただけで完成とは扱わない。
最後に内容・図・リンクを照合し、日本語は利用可能なkotonohaで推敲する。
事業目的、大枠の処理、変更するなら見る場所を読者として追えるか確認する。
ソース・依存定義・ロックファイル・DBを変更せず、発見した不具合は会話へ返す。
再実行は不足と変化だけを補い、完了報告は会話内に短くまとめる。
