# Codex UX Stack：使い方

通常は`$ux`へ目的を伝えます。専門Skillを選ばず、相談から分析・再設計・実装・確認を必要な範囲で依頼できます。
導線図・共同編集に集中したい場合は、[ux-visual-designの直接利用](visual-design.md)もできます。

[English](../en/codex-ux-stack/usage.md) | **日本語**

[概要](README.md) · [導入手順](installation.md) · [検証範囲](validation.md) · [docs一覧](../README.md)

## 共通の入口

```text
$ux
このアプリで、利用者が目的を達成しにくい原因を調べてください。
必要なら画面構造や導線の見直し案も示してください。今回は提案まで。
```

レビューは`audit`による観察だけに固定しません。所見に応じてOOUIの構造分析や図・ワイヤーフレームによる再設計案を組み合わせます。
「指摘だけ」なら大きな設計成果物を付け足しません。「設計まで」なら実装せず、「ファイル変更なし」なら対話上の提案までに留めます。
コードの改善まで依頼した場合は、必要な設計整理、実装、ブラウザー確認と再評価へ進みます。
小さな文言・CSS修正では対象箇所の確認に絞り、設計契約一式や全体監査を一律に要求しません。

通常の入口は`$ux`です。専門機能を直接使う場合は`$ooui-design`、`$ux-visual-design`、`$ux-gan-harness`を指定できます。
以下のハーネスコマンドは、その実行部品を直接使う場合の操作です。

## 子プロセスの権限とMCPの診断

1.2.0以降の新しい監査・改善では、各ロールを`workspace-write`で起動します。MCPの起動や画像保存に必要な書き込みを許可し、監査役にはアプリを編集しないよう指示します。監査中にソースが変わると停止し、差分を保持します。`audit`は作業範囲を表すモードであり、OS上のread-onlyを意味しません。

```bash
ux-gan-harness doctor --project /path/to/app --check-mcp
ux-gan-harness audit --project /path/to/app --url http://localhost:3000 --browser local-playwright --role-sandbox workspace-write
ux-gan-harness resume RUN_ID --project /path/to/app --role-sandbox workspace-write
```

`doctor --check-mcp`はモデルを呼ばず、専用のローカルMCPを初期化し、ツール一覧の取得、3回の操作、画像とreceiptの保存まで確認します。証拠は一時領域で照合してから削除します。登録済みのBrowser PluginやPlaywright MCPが子CLIで使えることは、実際の監査で別途確認します。

専用MCPは子CLIの起動時に初期化を待ち、依頼された監査・改善の操作をその呼び出し内で実行できる承認設定を渡します。個人設定や既存MCPの承認ルールは変更しません。`tool_approval`で止まる場合は、使ったMCPの承認設定を確認してください。MCPへ直接接続するdoctorだけでは、子Codexのツール承認やモデル認証までは確認できません。

既存runは保存済みの権限を引き継ぎます。権限の記録がない旧runは修正役以外をread-onlyとして扱い、上のresume例で切り替えられます。新しく実行する工程だけに適用し、完了済みの記録は変更しません。新規runをread-onlyにする場合は`--role-sandbox read-only`を指定します。修正役は常にworkspace-writeです。

起動ごとの`invocation.json`に実効権限・通信設定・一時領域を記録します。構造化出力を得られずに止まった場合は、同じ場所の`diagnostic.json`と`events.jsonl`を確認してください。認証失敗をブラウザーの障害として再試行せず、ブラウザー経路の失敗だけを記録してローカルMCPへ切り替えます。HOMEとCODEX_HOMEは維持し、一時データをrun内へ分離します。

## 新規アプリを設計・実装する

アプリのフォルダーでCodexを開き、`$ux`を指定します。自動選択の候補にもなります。

~~~text
$ux
文書と閲覧グループを扱う社内管理アプリを設計し、実装してください。
対象・属性・関係、一覧と詳細、関連への移動、操作と状態保持を先に整理してください。
その設計をProduct Design / Build Web Appsへ引き継いで見た目と実装を進め、
必須機能、Mobile表示、未保存の入力、エラーからの復帰を実画面で確認してください。
画面を煩雑にせず、不要な装飾・説明・常設要素を増やさないでください。
日本語UIの文言と設計メモは、利用可能なkotonoha（未導入ならyomiyasu）で整えてください。
~~~

利用者と機能は具体的な案件に合わせて指定します。短い設計メモを使い、既存仕様があれば再利用します。
部分修正では必要な確認だけ行い、全体の再設計や設計書一式の追加は行いません。
設計だけを依頼した場合は、実装やハーネスを開始しません。

OOUIは複数の対象を探索・比較・編集する場面で優先します。対象が確定している操作や、
意味のある固定手順ではタスク起点も使えます。検索は集合の絞り込み、一括操作は選択集合への操作として
整理し、対象範囲と結果を示します。採用した使い分けと理由を設計メモに残します。

日本語のラベル、説明、空状態、エラー文は、意味と対象名を保って推敲します。短いラベルを長文化せず、未導入でも文言確認を続けます。[日本語Skillの導入手順](../kotonoha/installation.md)を参照してください。

## 実装済みアプリをレビュー・改善する

アプリのフォルダーでCodexを開き、`$ux`へレビューや改善を依頼します。
URLと起動手順は、指定内容やREADME、起動済みサーバーから確認します。

~~~text
$ux
このアプリを初見ユーザーとして画像からレビューし、
類似アプリの良い点も画像付きで比較して、修正と再確認を自動で反復してください。
専門用語を知らない人でも主要操作を迷わず完了できることを優先し、
指摘のたびに説明やボタンを増やして画面を煩雑にしないでください。
~~~

実行したコマンド、RUN_ID、処理段階を表示します。調査・修正・評価は別々のCodex実行です。
元の会話のAIが、自分のレビューに置き換える手順にはしません。

## レビューだけにする

~~~text
$ux
画像と操作からレビューし、docs/ui-ux-review.mdに具体的な改善案をまとめてください。
必要なら画面構造や導線の再設計案も示してください。アプリのコードは変更しないでください。
~~~

auditは画像と資料を保存し、アプリを修正しません。reviewedはレビュー作成の完了で、アプリの合格ではありません。

## ターミナルから使う

PATH・URL・コマンドを自分のプロジェクトに置き換えてください。

~~~bash
ux-gan-harness doctor --project /path/to/app
ux-gan-harness audit --project /path/to/app --url http://localhost:3000

ux-gan-harness run \
  --project /path/to/app \
  --url http://localhost:3000 \
  --start-command 'npm run dev -- --host 127.0.0.1' \
  --test-command 'npm test' \
  --test-command 'npm run build'
~~~

起動済みサーバーは再利用し、自身が起動したプレビューだけを終了します。
作成・削除の確認にはテスト用データや使い捨て環境を使います。
必須チェックを指定してください。省略時は調査役が既存のチェックを特定します。特定・完了できなければ合格にしません。

## オプションと完了条件

### 局所変更を確認する

ボタンやフォームなど、対象を限定した確認には`focused`を指定します。

~~~bash
ux-gan-harness audit --project /path/to/app --url http://localhost:3000 \
  --profile focused --focus '設定画面で表示名を保存する操作と、取消後の入力保持'
~~~

既定ではDesktop・Mobileを確認し、初見・誤操作の視点で再確認します。
画面幅を限定する場合は`--viewport desktop`などを指定します。複数指定も可能です。
参考URLがなければ類似サービス比較を省略し、指定した場合は比較が必要になります。
検証対象と除外範囲はレポートへ残します。`passed`でも、その範囲の確認結果であり、アプリ全体の合格ではありません。

引数を追加しない従来の実行は`full`です。3種類の画面幅・4つの視点・参考比較を維持します。
`resume`は保存済みの範囲を引き継ぎ、旧記録にprofileがなければ`full`として扱います。

ローカルブラウザーの`ux_inspect`は、直近12枚の画像の実URL・画面幅・パス・ハッシュも返します。
実URLはリダイレクト後の値です。画像を見た後に、この記録値を根拠へ転記します。
不一致では実行を止め、対象の画像IDと不一致項目を表示します。保存済み結果を編集して合格にしないでください。

### オプション一覧

| オプション | 用途・既定値 |
|---|---|
| --project PATH | 対象アプリ。既定は現在のディレクトリ |
| --url URL | HTTP(S) URL。audit/runでは必須 |
| --start-command COMMAND | URLに到達できない場合の起動コマンド |
| --test-command COMMAND | 必須チェック。複数指定可 |
| --review PATH | 既存レビュー。省略時は対象アプリの最新レビュー |
| --reference-url URL | 比較候補の公式URL。複数指定可 |
| --max-iterations N | 修正反復の上限。既定5回 |
| --phase-timeout SECONDS | 評価役の固定時間上限。既定0（固定上限なし）。正数を明示した場合は尊重する |
| --idle-timeout SECONDS | 有効な進捗がない評価役を止めるまでの時間。既定900秒 |
| --browser auto | Browser plugin → Playwright MCP →失敗を記録してローカル経路 |
| --browser local-playwright | 専用のローカル経路を明示選択 |
| --model MODEL | その実行だけCodex設定のモデルを上書き |
| --brief TEXT | 対象ユーザーや重点タスクを補足 |
| --profile full\|focused | 既定full。focusedは対象限定の確認 |
| --focus TEXT | focusedの対象画面・操作。必須、複数指定可 |
| --viewport desktop\|tablet\|mobile | focusedで確認する画面幅。複数指定可 |

通常は短い時間上限を付けず、進捗と回復状況を追ってレポート完成まで待ちます。観察は途中保存し、照合で見つかった記録の不一致を評価役が最終出力前に修正します。停滞・モデル接続切断からは同じ実行IDで最大2回再開します。同じ画像・操作・文言の反復だけでは待機時間を延長しません。認証・承認不足、明示した時間上限、利用者の中断、修正途中の処理は自動で再試行しません。

最大回数は従来どおり修正と再レビューを1回と数え、既定5回です。2回連続で改善しなければ停滞として終了します。再開しても反復・回復の消費回数は戻りません。起動・ブラウザー操作の制限と、修正役・必須コマンドの既定1800秒は維持します。

`resume`は保存済み設定を維持します。`resume RUN_ID --phase-timeout 0 --idle-timeout 900`で今後の時間設定を明示変更でき、変更は履歴へ残ります。最終結果のない停止でも、run内の`partial-review.md`から確認済みの観察・残項目・停止理由を追えます。途中結果を合格や全体の確認完了とは扱いません。

画像と実操作から問題を記録し、コードは原因調査と修正に使います。
指摘を共通の原因でまとめ、1回に最大3グループを修正します。
別の評価役が、前後の画像と操作から次を確認します。以下は既定のfullの条件です。

- Critical・Highが解消している。
- 必須フローがDesktop 1440×900、Tablet 768×1024、Mobile 390×844で完了できる。
- 該当するエラー・キャンセル等の状態と、4つの利用者視点で再確認した。
- 必要なテスト、画像、比較資料がある。
- 新しい重大問題や主要画面の煩雑化がない。

OOUIの構造は画面別の情報設計・操作性へ、覚える・探す・推測する・比較する・往復する負担は
フローの摩擦と簡潔さの評価へ記録します。機能の充足、表示不具合、実操作の完了も別々に確認します。
必須情報の隠蔽、再入力の増加、状態の喪失も主要操作の悪化として扱い、要素数やクリック数だけで良否を決めません。
操作数の対象フローと数え方は理由欄へ残します。AIによる所見と、人間の認知負荷の測定は区別します。

Medium・Lowの細部は残件として保存できます。上限到達や2回続けて改善しない場合は未達成です。
新機能追加、自動commit・reset・デプロイは行いません。

| 状態 | 意味 | 終了コード |
|---|---|---|
| reviewed | auditのレビュー作成が完了 | 0 |
| passed | runの改善条件を満たした | 0 |
| incomplete | 上限・確認不足等で条件が残る | 2 |
| stalled | 2回続けて改善しない | 2 |
| blocked | 環境不備・画像欠落・出力不正・想定外の変更等 | 1 |
| cancelled | 中断。差分・画像を保持 | 130 |

## 成果物とEvidence

| 対象アプリ内の保存先 | 内容 |
|---|---|
| docs/ui-ux-review.md | 指定11章、確認した画面・フロー数、重要度別件数、改善順 |
| docs/ui-ux-reference-apps.md | 比較画像、良い工夫、適用案、採用しない部分、出典・日付 |
| docs/ui-ux-fix-report.md | 解消した指摘の前後画像、検証、簡潔さの評価、残件 |
| docs/ui-ux-review-assets/RUN_ID/ | 役割・反復ごとのPNG |
| artifacts/ux-gan/RUN_ID/ | 状態、JSON結果、操作範囲、検証ログ、元のレビュー |

Evidenceは画像表示と相対リンク、対象UI、操作、表示幅を含みます。
PNGの実在・読み取り・サイズを検査します。ローカル経路ではブラウザーの撮影記録とハッシュを照合します。
指摘と画像の画面・フローが対応することも検査します。解消扱いには別の評価役による同じフローの結果画像が必要です。
類似アプリは公開デモを優先し、公式資料の画像は実操作と区別します。

画像はtest-results/の外に保存し、各ロールの終了時にdocsへ退避します。
元のレビューと画像、各実行のレポートも保存します。手動編集と競合した最新レポートは上書きしません。
発見した総数と、実際に確認した画面・フロー数を区別します。
共通設計基準の要約、版、参照パス、ハッシュは各ロールのprompt.txtにも保存します。

## 中断と再開

~~~bash
ux-gan-harness resume 20261004T120000Z-example --project /path/to/app
~~~

RUN_IDは実際の値に置き換えます。修正後の評価が失敗した場合は、その評価から再開します。
修正自体が中断・未検証になった場合は差分を保持し、新しいaudit/runで確認します。
別の作業でソースが変わった場合は新しいaudit/runを開始します。
ハーネス同士はロックで重複実行を防ぎます。同じファイルの同時編集は確実に帰属できないため、修正中は並行編集を避けます。
旧版の実行を再開した場合、新しく動くロールには現在の基準を渡します。完了済みの実行は再評価しないため、
新しい基準で確認するには新しいaudit/runを開始してください。

## 過去の指摘と日本語レポート

設計・レビュー・修正の開始時に、既存の設定で参照できるBasic Memoryから関連する過去の指摘を検索して読みます。
今回の目的、利用者、対象・操作、制約と、ノートの文脈・適用範囲・例外を照合します。
対象外や古い条件をそのまま適用せず、現在の依頼を優先します。今回の問題と解消は新しい画像と操作で確認します。
適用したノートと理由は既存の設計メモや所見へ短く残します。未導入・検索失敗・該当なしを区別し、作業を続けます。
この手順ではMemoryの読み取りだけを行います。

日本語UI文言、設計メモ、レビュー・比較・改善レポートの下書きは、kotonohaで一度推敲することを推奨します。未導入なら利用可能なyomiyasuを使い、両方を重ねて適用しません。
主張、専門用語、数値、ID、条件、確認結果、根拠、断定の強さを保ちます。ハーネスの子ロールは説明欄を整えてからJSONとして返します。
生成済みレポートや過去の保存版は保持します。未導入でも執筆・文言確認を続けられます。

## 他の収録ツール

ooui-designで決めた画面構造を渡したうえで、Product Designはデザイン案や試作、Build Web Appsは実装・ブラウザー確認、
web-design-guidelinesは観察した問題のコード確認に使います。

~~~text
Product Designを使って、予約一覧の主要操作が分かりやすいデザイン案を比較してください。
~~~

~~~text
$web-design-guidelines 実画面で見つかったフォームのラベルとエラー表示について、UIコードを確認してください。
~~~

--deepで導入したux-critiqueは追加の批評に使えます。

~~~text
$ux-critique --standard
予約詳細で、初めて使う店舗スタッフが変更と取り消しを迷わず行えるかレビューしてください。
~~~

これらは別の依頼です。ハーネスの成功や、未確認部分の動作保証を意味しません。
