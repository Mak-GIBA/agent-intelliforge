# 旧フローを保つkotonoha 4.1.0の検証

3.0.0の工程と詳細規範を移植した候補を、旧版と実際に起動して比較した記録です。素材は合成例です。モデルの内部推論、認証情報、利用者の実際の原稿は保存していません。

## 条件と実行回数

`gpt-6.1-sol`、推論設定`medium`を固定し、各呼出しを新しいセッションで実行しました。利用者のSkillと設定は呼出し単位で除外し、一時プロジェクトに対象のSkillだけを配置しています。原典や規範をまとめてプロンプトへ渡す方式ではなく、モデルが必要な実ファイルを読みます。

初回は旧版24稿と候補24稿を生成し、候補を2回修正して、それぞれ候補側の24稿を再生成しました。生成は計96回、4用途ずつの比較評定は計18回です。旧版の24稿は、入力・設定・資材の同一性を確認して再利用しました。再生成した旧版稿として数えません。

元の上限は60分、1呼出しは180秒です。最初の契約記録から最後の評定ファイル作成まで、ローカルで約40.2分を観測しました。当初は候補修正を一巡と予定しましたが、未解決の指摘を受けて元の時間枠内で二巡へ変更しています。失敗の自動再試行や、完成稿だけを試験外で修正する操作はしていません。

## 保留と修正

| 実行 | 結果と対応 |
|---|---|
| native-r1 | 否定の範囲、比較関係、説明末尾の重複、見出し階層と説明不足で保留。候補の該当規則を補足 |
| native-r2 | 初回の問題は解消。重要性の主張の欠落と、診断における見出し点検の不足で保留。意味保持と点検範囲を補足 |
| native-r3 | 24対の実出力・評定・参照・検査を照合し、候補の重大な誤り、未解決の回帰、参照漏れの指摘なし |

旧規範の保持部分は修正していません。補足はその外へ追加し、移植元9資料と許可した配線変更の照合を維持しました。

2巡目には、資料のcatの後に未存在ディレクトリを検索し、コマンド全体が終了コード2になった記録がありました。初期観測器は終了コード0の出力だけを調べたため、実際に返却された仕上げ・レビュー資料を未読と判定しました。[可視性の再照合](route-audit.json)では、原稿・評定・規範を変えず、返却本文と資料全文の一致を確認しています。元の観測結果と[補正前の品質記録](initial-route-quality.json)も残しました。この補正後も2巡目の文章上の問題は保留のままで、3巡目の再生成・評定によって確認しています。

## 記録の読み方

- [audit.json](audit.json): 条件、回数、時間枠、採用状態、旧版資材の版、確認の限界。
- native-r1〜native-r3: 実出力、ツールの応答、入力hash、モデル使用量、別実行の評定、実行コードのスナップショット。
- round1／round2のquality・guides: 保留結果とその時点の規範。後の補足で上書きしていません。
- [quality.json](quality.json): 採用した3巡目の24対と証拠ファイルのhash。
- [review.json](review.json)・[verification.json](verification.json): 規則・原典・実出力・評定を確認した採用前の記録。

配布元のUPSTREAMS.jsonにあるquality_sha256とreview_sha256は、ここにある同名ファイルへ対応します。比較対象の規範と原典はquality.jsonのadapter_sha256へ対応します。採用状態を更新するUPSTREAMS.jsonと、再生成可能なresources.jsonはその対象から除いています。

## 限界

同じモデルの別セッションによる自動評定で、人間の独立評価ではありません。X/Yの版名を伏せ、両方の誤りと相対的な劣化を評定しています。温度は制御していません。

実モデルの実行環境はLinuxのCodexです。両ホスト向け配布の構造・原典hashとPython実行は確認していますが、WindowsとClaudeの実機モデルによる追加評価は行っていません。

24用途は候補の修正にも使用しており、未使用課題での追試ではありません。旧版と候補では固定した上流資材の版も異なるため、差を配置変更だけの効果とは扱いません。資料本文がツール応答に含まれたことは確認できますが、内部の適用順や回数は観測できません。処理時間、token使用量、原典の全規則や他モデルでの挙動の同等性は一般化しません。

このPCの導入済み旧3.0.0については、作業前に固定した54ファイルと同じhashであることを確認しました。
