# Repository Director

[English](../en/repository-director/README.md) | **日本語**

[導入・移行](installation.md) · [使い方](usage.md) · [検証範囲](validation.md) · [docs一覧](../README.md)

リポジトリの目的と実装を開発者向けの文書にまとめ、その資料を参照して開発を進めるSkillです。
既存コードから仕様書・AGENTS・READMEを後付けする用途と、新規開発の両方に対応します。
GitHubのIssue・PR・Projects、GitLabのIssue・MR、コミットの説明も扱います。
既存規則を尊重しながら、作業ブランチでの変更・検証からPR/MR作成、別エージェントによるレビュー・取り込みまでを任せる運用を設定できます。
対象・許可操作・必須条件を最初に合意し、既存の合意がPR/MR作成までならその範囲を守ります。[運用例](usage.md#ブランチからレビューと取り込みまで任せる)

旧GitHub Project DirectorとSpecKit Upstreamを統合した独自キットです。旧スクリプト・キットID・Skillの互換入口は廃止しました。
公式SpecKit、専用JSON、承認台帳、研究ツールを必須にしません。既存の文書・SpecKit資材・履歴は保持できます。

## 文書の構成

ルートのREADMEは概要、導入、使い方、主なコマンド、詳細文書とライセンスへの入口です。
AGENTSはエージェントの作業ルールと参照先に絞ります。標準のdocsは次の3冊です。

| 文書 | 内容 |
| --- | --- |
| purpose.md | 事業目的、背景、利用者、提供価値、主要機能と対象範囲 |
| architecture.md | 注釈付きファイル構成、処理の入口、呼び出しとデータの流れ、設計上の要点 |
| development.md | 開発環境、実行・テスト、変更・レビューと運用手順 |

目的・概念・全体像は生成画像を中心に説明し、正確なファイル構成や処理経路は注釈付きツリーとMermaid、画面操作は実画面で補います。
図はプロジェクト内に保存し、本文・実装と照合します。既存の適切な図は再利用します。
事業背景や設計理由は残し、文書を作成した経緯や調査作業の報告は本文に載せません。
既存の日本語名・独自配置・索引・仕様書は再利用します。全関数の解説や、役割ごとの文書一式を一律に生成しません。

## 最初の依頼

対象リポジトリでCodexへ入力します。

```text
$repository-director
既存コードを調べ、仕様書とAGENTSとREADMEを整えて。実装は変えず、分からない業務要件は確認して。
```

対話が既定です。「お任せで」と指定すると、開発上の方針を選んで理由と仮定を残します。
事業目的、依頼者の合意、実行していない検証結果は推測しません。
インストールは対象プロジェクトを変更せず、文書整備は別の依頼で行います。
