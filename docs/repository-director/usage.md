## 既存コードから文書を整備する

```text
$repository-director
このプロジェクトのコード・テスト・既存資料を調べ、目的・設計・開発の文書とAGENTSとREADMEを整えて。
実装は変更しないで。重要な不明点は対話で詰めて。
```

まず全体像と対象範囲を把握し、機能・権限・主要処理・データ・テストを追って本文を作成します。
標準のdocsはpurpose.md、architecture.md、development.mdの3冊です。事業目的・背景を独立文書へ置き、READMEは概要・導入・使い方の入口にします。
設計には注釈付きのファイル構成、入口の一覧、担当ファイルを添えた呼び出し・データの流れの図を載せます。
目的・背景・主要概念・全体像は生成画像を入口にし、正確な呼び出しはMermaid、画面操作は実画面、計測結果は実データから作る図で説明します。
画像は本文の近くに置き、短い説明と代替テキストを付けます。既存図が十分なら再利用し、画像生成が利用できない場合は未生成の範囲を会話で伝えます。
既存の仕様書・独自名・索引は再利用し、詳細を複製しません。
実装から確認した現状、合意済み要件、改善提案を分け、矛盾や未実装を隠しません。
調査範囲や作成経緯を本文へ載せず、動作・検証の重要な未確認事項だけを該当箇所へ残します。
実行していないテストを成功とは記載しません。
文書整備だけではソース、依存、ロックファイル、DBを変更しません。

```text
packages/searchだけを対象に、お任せで方針を整理して。既存のルールは残して。
```

モノレポは対象外のパッケージを変更せず、親の方針を守ります。
お任せでも事業上の目的・正式な要件を作りません。不明点と仮定を残します。

## 新規開発と通常の変更

```text
$repository-director
社内文書を検索するアプリの目的と要件、設計、検証方法、開発方針を整理して。
```

```text
$repository-director
検索方式を変更して。運営方針と関連設計を読み、実装・テスト・説明文書を一緒に更新して。
```

目的・利用者・制約から要件と設計を整理します。方式の不確実性が高い場合は利用可能な研究Skillで根拠を調べます。
小さな変更で全資料を作り直さず、関係する仕様と検証条件だけを見直します。

## ブランチからレビューと取り込みまで任せる

Git運用に詳しくなくても、対象リポジトリで次のように依頼できます。

```text
$repository-director
作業用のブランチで変更し、テスト、コミット、push、PR作成まで任せたい。
別エージェントがレビューし、必須条件が揃えば、そのレビュワーにmainへのマージまで任せたい。
既存のチームルールがあれば合わせて運用を整えて。
```

既存の方針・取り込み先・テンプレートを調べ、任せる操作と条件を短く示して合意します。
未設定なら「別エージェントがレビューし、許可と必須条件が揃えば本人がmergeする」形まで含めて提案します。
合意は既存の運営方針へ記載し、AGENTSから参照します。Git運用だけの設定では仕様書一式を生成しません。
合意済みの範囲は毎回聞き直さず、継続作業では同じブランチとPR/MRを更新します。

```text
作業ブランチ → 変更・検証 → コミット → push → PR/MR → 別エージェントのレビュー → レビュワー本人がmerge
```

無関係な変更を混ぜず、目的ごとにコミットします。PR本文は問題と変更後の動作から始め、
方法を選んだ理由、実際の確認結果、未確認や互換性への影響を変更の規模に合わせて伝えます。
必要な検証が終わらない場合は準備完了とせず、合意した範囲で相談用のDraftにするか、ローカルの説明案を用意します。
接続できなければ可能なローカル作業を進め、未push・未投稿を明示します。再試行前に既存の結果を確認します。

mergeは明示依頼または対象範囲の合意がある場合に実施します。既存の合意がPR作成までならその範囲を守ります。
レビュワーは実際の差分・コード・文書・検証結果・最新CI・承認条件を確認し、指摘があれば実装担当へ返します。修正後は新しいheadで確認し直します。
別エージェントが使えない場合や必須条件が揃わない場合は不足を伝え、実装担当の自己レビュー・mergeでは代行しません。同じアカウントの別エージェントを人の承認とは扱いません。
取り込みの合意は、リリースやブランチ保護の変更の許可にはなりません。

開始・再開時は関連ブランチとPR、未コミット変更、依存と取り込み順を確認します。
独立した作業は別ブランチ・worktreeへ分け、同じ目的の続きは再利用します。
取り込み前は最新のbaseと組み合わせて検証し、共通の生成物は正本の統合後に再生成します。

```bash
repository-director work-status --project /absolute/path/app --base main --compare work/related
```

`--base`は必須で、実際の取り込み先を指定します。`--compare`は省略・複数指定できます。
リポジトリ全体のブランチ、追跡先、worktree、未コミット変更と共有パスをJSONで集計します。ファイル本文は返しません。
通信やGit状態の変更は行わず、remoteの最新状態と実際のマージ競合は未確認として返します。
共有パスが空でも動作上の整合性は未確認です。squashの取り込み判定やブランチの自動削除にも使いません。
解決できない参照や取得失敗はエラー・警告とし、共通祖先が特定できない比較は空配列でなく`null`を返します。
外部フィルターは無効化し、影響する作業ファイルの状態は候補として返します。submodule内部の作業ファイルは未確認です。

## 文書ヘルパー

```bash
repository-director inspect --project /absolute/path/app
repository-director init --project /absolute/path/app --mode existing
repository-director init --project /absolute/path/app --mode existing --apply
repository-director check --project /absolute/path/app
repository-director check --project /absolute/path/app --base main
```

`init`は3冊の下書きとREADME・AGENTSの案内の配置です。新しい索引ファイルは既定では作りません。
既存の索引があれば再利用します。本文を調査・策定するAI処理ではありません。
Skillがコードを調べて内容を仕上げます。下書きのまま整備完了とは報告しません。
既存本文と独自ルールは保持し、同じ処理の再実行で節を重複させません。
独自の正本には `--document requirements=specs/current.md`、索引には `--index docs/navigation.md` を指定できます。
役割名は purpose / policy / requirements / architecture / core / verification です。
役割名は既存の指定との互換性のために残しています。複数の役割を同じ既存文書へ対応付けられます。
完成した本文からだけ非表示のdraftマーカーを外します。CLIと`check`は下書きを区別します。
`--approach delegate`はお任せの下書き方針、Claudeの共通入口には `--agent claude` を使います。

Pluginでは次の入口を使います。WindowsでもBashに依存しません。

```text
intelliforge kit-run repository-director --agent claude -- inspect --project <target>
intelliforge kit-run repository-director --agent claude -- check --project <target>
```

`check`の終了値は0が構造エラーなし、1がリンク等の構造エラー、2が実行・入力エラーです。
下書きや文書の入口から到達できない文書は確認候補です。意味的な一致やテスト結果の真実性は内容と実測で確認します。

## 変更説明とリモート操作

```text
この差分のコミットメッセージとPR本文を作って。目的と変わる動作、確認結果、残件が伝わるかも確認して。
```

```text
GitLabのこのMRをレビューして。指摘は会話に返して。
```

元の依頼・差分・検証結果と文章を照合します。未確認を隠さず、短い変更は短く説明します。
レビューや下書きの依頼だけでは投稿しません。GitHub/GitLabの実操作は接続済みツールまたは公式gh/glabを使い、対象・権限・重複を確認します。
合意済み範囲の投稿は同じ許可を聞き直さず、反映後に再取得して確認します。
